## 1. Summary

- **The threshold is passed: a bind-mounted repository and the CLIs work as a second uid →
  the "own uid" step may go into M3.** It has two conditions and one dependency
  (section 4).
- **What works as the second uid** (the agent is 1500; LADO is the uid of the workspace's
  owner, as today):
  - tmux on its own socket, `git status` and `log` in the bind-mounted repository;
  - `--version` of the four CLIs with their own HOME;
  - `uv run` of a script with a dependency.
- **Writing to the bind-mounted repository as the second uid does not work as is:** the
  host's files are `755`/`644`. ACLs on the host fix it:
  - `setfacl -R -m u:1500:rwX,d:u:1500:rwX,d:u:<owner>:rwX,m::rwx,d:m::rwx`;
  - it works both ways, and for files the host creates later;
  - a shared group does not fix everything: a new host file with umask 022 is no longer
    writable for the agent.

  The reverse layout (B: the agents are the human's uid, LADO has its own uid) gives bind
  both ways with no setup. But then LADO itself cannot write to the repository:
  `git worktree add` fails.
- **What of LADO's the agent can reach.** Closed:
  - `server-token`, the projects' secrets, the git servers' tokens, LADO's secrets
    (Settings);
  - LADO's tmux socket, LADO's processes (signal, ptrace, `mem`, `environ`), the UI's API
    without the token.

  **Open (holes):**
  - `~/.lado` has mode `755`, `lado.db` `644`. The agent copies the database and reads it:
    23 tables, the projects, the git servers' addresses;
  - the listings of `~/.lado` and `/home/lado`.

  This must be closed before the uid step: `LADO_HOME` with mode `700`.
- **A dependency on M2.** The hooks and `lado mcp` run from the agent's process and open
  `lado.db` themselves. From another uid they fail: `sqlite3.OperationalError: attempt to
  write a readonly database`. So the uid step is possible only after the Agent API (M2:
  hooks and MCP through `lado server`).
- **`codex sandbox` as the second user, settled:**
  - it needs user namespaces: under runc there are none (Docker's seccomp); with a seccomp
    that allows `unshare`, plus AppArmor `lado-runner-lite`, it works; under runsc it works;
  - HOME matters only with a **system** `bwrap` in PATH (as in E15's rootfs): then without
    a writable HOME codex 0.162 and 0.172 fail with E15's error `bwrap: execvp
    codex-linux-sandbox: No such file or directory`, and with the agent's HOME they work;
  - LADO's image has no system bwrap, and codex works there without a HOME.

## 3. What was done

### 3.1 Layouts and preparation

The container is started as the image's documentation says:

```
docker run -d -v e10-x-home:/home/lado -v "$WS:$WS" -e LADO_REPOS="$WS" \
  -e LADO_GIT_NAME=… -e LADO_GIT_EMAIL=… -v "$SEC:/run/secrets:ro" lado:m0-e10
```

Plus `-v m0/e10:/e10:ro` with the scripts. `$WS` is the host user's folder with the
repository, `$SEC` is their `700` folder with a `600` file.

- **A, as today.** The entrypoint gave `lado` the owner's uid (1001). The agent is a new
  user `agent`, uid 1500, `/home/agent` with mode `700`.
- **B, the reverse.** The workspace's top folder was given to uid 1600, so the entrypoint
  gave `lado` 1600. The repositories inside belong to the host's user (1001); the agent is
  uid 1001. In the image this would be a change of the entrypoint.

The second user, the helper and the sudo rule are created by `docker exec -u 0`
(`in.sh prep`). The image itself gives no root after start: the entrypoint removes its own
sudo rule.

**The canaries** are created by LADO itself where it can:
- `lado.db` and `server-token`: starting the server;
- a project secret: `lado project create e10` and `lado project set e10
  E10_CANARY_PROJECT --secret`;
- a git server's token: `lado git-server add https://gitlab.e10.invalid --token --kind
  gitlab` (it saved it, though the address leads nowhere);
- LADO's tmux server: `tmux -L lado new …`.

By hand, with the modes of LADO's code (folder `700`, file `600`): only LADO's secret from
Settings (`~/.lado/secrets/CLAUDE_CODE_OAUTH_TOKEN`): it has no CLI.

### 3.2 How LADO starts a process as the agent's uid (`logs/e10-24-launch.md`)

| way (from `lado`, no capabilities) | A, B | under runsc with `no-new-privileges` |
|---|---|---|
| `sudo -n -u agent -H` with the rule `lado ALL=(agent) NOPASSWD:SETENV: ALL` | works; `-E` passes the variables | no: "\"no new privileges\" flag is set" |
| a helper `lado-as-agent` (setuid root, `root:lado 4750`, `initgroups` + `setgid` + `setuid`, a check that root cannot be regained) | works, passes the environment | no: `Operation not permitted` |
| `setpriv --reuid agent` | no: `setresuid failed: Operation not permitted` (no `CAP_SETUID`) | no |
| `runuser -u agent` | no: "may not be used by non-root users" | no |
| `docker exec -u 1500:1500` (the runtime; like `runsc exec --user`) | works | works |

The agent cannot get back:
- `sudo -n true` and `sudo -u lado`: "a password is required";
- `lado-as-agent`: "Permission denied" (not in the group `lado`);
- `su lado`: "Authentication failure".

### 3.3 What the agent reaches of LADO's (`logs/e10-21-reach.md`)

| what | A | A, the agent in group lado | B |
|---|---|---|---|
| read `lado.db` as a file | **hole** (`644`) | **hole** | **hole** |
| copy `lado.db` and open it (23 tables, the projects, the git servers' addresses) | **hole** | **hole** | **hole** |
| open `lado.db` with sqlite in place | closed ("attempt to write a readonly database") | closed | closed |
| listing `~/.lado` (`755`) and `/home/lado` (`755`) | **hole** | **hole** | **hole** |
| `server-token` (`600`) | closed | closed | closed |
| a project's secret, a git server's token, LADO's secret (folders `700`, files `600`) | closed | closed | closed |
| `/run/secrets` (the host's `700` folder) | closed | closed | **open**: its owner is the agent's uid |
| LADO's tmux socket (`/tmp/tmux-1001`, `700`) | closed | closed | closed |
| the UI's API without the token (`127.0.0.1:8765/api/system`) | closed (401) | closed | closed |
| `lado ls` on `LADO_HOME` (as a hook or `lado mcp` would) | fails: "attempt to write a readonly database" | fails | fails |
| LADO's processes: signal, `PTRACE_ATTACH`, `mem`, `environ`, `root`, `fd` | closed (EPERM, EACCES) | — | closed |
| the command lines of LADO's processes in `ps` | visible | visible | visible |

Everything LADO creates itself with `700`/`600` is closed. Everything created with the
default umask is open for reading: `lado.db`, `server.json`, lock files. A real session
has more such files (the agents' messages, artifacts); there was no session here.

### 3.5 A bind-mounted repository both ways (`logs/e10-23-bind.md`)

The order: the host creates its file → the agent appends to the host's file and to a new
host file, creates its own file and folder, `git add` + `commit` → the host appends to the
agent's file, creates a file in the agent's folder, makes its own commit, `git fsck`,
deletes the agent's folder.

| | A as is | A + ACL on the host | A + a shared group | B as is |
|---|---|---|---|---|
| the agent: writes to the host's files, a new file, commit | **no** (`Permission denied`, `index.lock`) | yes | yes | yes |
| the host: writes to the agent's files, a file in its folder, commit, fsck, delete | — (the agent created nothing) | yes | yes | yes |
| the agent: a file the host created **later** (umask 022) | no | **yes** (default ACL) | **no** | yes |
| LADO itself: `git worktree add` in the repository | yes | yes | yes | **no** (`cannot lock ref … Permission denied`) |

- **ACL on the host:** `setfacl -R -m u:1500:rwX,d:u:1500:rwX,d:u:1001:rwX,m::rwx,d:m::rwx
  <repo>`. The `acl` package was already on the runner.
- **A shared group:** `chmod -R g+rwX`, setgid on the folders, `core.sharedRepository=group`,
  the agent in the owner's group, the agent's umask `002`. An agent put into the group
  `lado` reaches of LADO's the same as without it: the open rows are those of column A.

### 3.6 `codex sandbox` and HOME (the question from E15)

The environment: runc + seccomp userns + `lado-runner-lite`, the agent is 1500.

| codex | HOME | without a system bwrap (LADO's image) | with a system `bwrap` 0.8.0 in PATH (as in E15's rootfs) |
|---|---|---|---|
| 0.162.0 | `/home/agent` (its own, writable) | yes | yes |
| 0.162.0 | none (`/nonexistent`) | yes, with the warning "could not create PATH aliases" | **no**: `bwrap: execvp codex-linux-sandbox: No such file or directory` |
| 0.172.0 | `/home/agent` | yes | yes |
| 0.172.0 | `/nonexistent` | yes, with the same warning | **no**: the same error as in E15 |
| 0.172.0 | `$HOME` not writable (`555`) | yes, with the warning | — |
| 0.172.0 | `CODEX_HOME` to a folder that does not exist | no: "CODEX_HOME … does not exist" | — |

The mechanism. codex puts into `$HOME/.codex/tmp/arg0/codex-arg0…/` a link
`codex-linux-sandbox` to itself and adds it to PATH. A system `bwrap` starts the helper by
name through PATH: without the link there is none. codex's built-in path does without it.
So the agent needs **its own writable HOME** (or an existing `CODEX_HOME`), and that is
enough.

### 3.7 LADO's image under runsc

- **As the documentation says** (`--runtime runsc`), the container exits at once
  (`Exited (1)`):
  - `sudo: effective uid is not 0, is /usr/bin/sudo on a file system with the 'nosuid'
    option set…`;
  - setuid did not work in gVisor: the root is `overlay rw`, `sudo` is `-rwsr-xr-x`;
  - the entrypoint exits on this error.
- **With `--security-opt no-new-privileges`** the entrypoint skips the root step and warns
  that `lado` stays uid 1000 and `LADO_REPOS` is not writable. The server starts; the
  kernel inside is `4.19.0-gvisor`.

## 4. What it means for the plan

- **The uid step in M3: yes, after M2 and with conditions:**
  1. **M2 first:** the hooks and `lado mcp` running as the agent's uid must not open
     `lado.db`. The Agent API through `lado server` (M2a) is a hard condition; without it
     the step breaks the statuses and the MCP tools.
  2. **`LADO_HOME` and LADO's home with mode `700`:** `chmod 700 /home/lado ~/.lado` at
     start (or umask `077` for the server), a check in `lado doctor`. Otherwise the agent
     copies `lado.db`. This is useful without the uid step too.
  3. **The agent's own HOME** (`700`), with the CLIs' configs in it. Override
     `CLAUDE_CONFIG_DIR` and `NPM_CONFIG_PREFIX` for the agent. The CLIs' logins live in
     LADO's home today and must move to the agent or be passed as variables (LADO's
     secrets are already passed so). Not checked with real logins (E4).
- **The bind layout.** I propose **A + ACL**: LADO stays the human's uid, the agents have
  their own uid, the installer (or `lado doctor --fix`) sets the ACL on the workspace. It
  works both ways and for the host's future files, and LADO itself writes to the
  repositories.

  Layout B is simpler for bind, but LADO loses writing to the repository: worktrees and
  merges would have to be done as the agent's uid through a helper. Also, everything owned
  by the human is open to the agents (`/run/secrets`).
- **Starting as the agent's uid:** inside today's image, a helper `lado-as-agent` (setuid,
  `root:lado 4750`, it can only "become agent") or a sudo rule. Both leave a setuid-root
  path in the container, although today the entrypoint removes it. Neither works under
  `no-new-privileges` or in gVisor. In the runner (M4, M5) the runtime sets the uid
  (`runsc exec --user`, `docker exec -u`): no helper is needed.
- **tmux:** the tmux server belongs to the agent; LADO connects after `server-access -a
  lado` (tmux ≥ 3.3; the image has 3.3a). Or LADO runs the tmux commands through the
  helper. LADO's own socket is closed to the agent.
- **`safe.directory '*'`** stays needed in A: the repository's owner is not the agent. Not
  needed in B.
- **`codex sandbox`:** in today's image under runc it is not there and will not be without
  user namespaces. Opening them (a seccomp with `unshare`, `setns`, `mount`,
  `pivot_root`, plus AppArmor with `userns,` and `mount`) means weakening the container. I
  propose not to open them, and to count on codex's inner sandbox arriving with runsc
  (M5). The agent needs its own writable HOME.
- **The image does not start under runsc** because of the sudo step in the entrypoint. For
  M4, M5: the runner must set the uid from outside, and the entrypoint must understand that
  there is no setuid (as with `no-new-privileges`).
- **For M2b:** the agent sees the command lines of LADO's processes (`ps`). LADO puts
  variables into tmux's `-e` only for popups (`tmux.popup_command`); worth checking that no
  secrets go there.

## 5. Problems and surprises; what was not done

- **Run `46060545517`:** the tag `ghcr.io/astral-sh/uv:0.13.9-python3.13-bookworm-slim`
  does not exist (`manifest unknown`). The wheel was built in `python:3.13-slim` with `pip
  install uv==0.13.9`: the same uv version as in the image.
- **Run `46060952416`:** the `docker run` had no image (my mistake in `lado_up`); the
  containers did not start.
- **Run `46061557817`:**
  - with `chmod 777` tmux answers `access not allowed` with rc=0, and the check wrongly
    counted `list-sessions` as passing. Fixed: the check reads the output;
  - the tail of a CLI's error was cut.
- **Run `46062509584`:** under runsc `docker exec -u agent` did not find the user ("no
  matching entries in passwd file"). An `/etc/passwd` changed inside the gVisor sandbox is
  not visible to Docker outside. Fixed: `-u 1500:1500`.
- **Runs `46060545517` to `46063457609`:** the snapshots did not match: an image
  `node:<none>` was left (pulled by digest, with no tag, so cleanup by tag did not see it).
  Cleanup now also removes by id. The runners are single-use, so the result is not
  affected.
- **Not checked:**
  - the CLIs' real logins and a real LADO session with agents (by the rules: no secrets);
  - Docker Desktop on macOS and Windows: there the owner and the ACL of a bind-mounted
    folder behave differently (virtiofs); the host's ACLs may not get through;
  - rootless Docker and userns-remap (E7).
- In the row "the host: writes to the agent's file", column "A as is" said "yes", but there
  was no agent's file: the host created it itself. The table above shows "—".
- **Time:** about 2.5 hours (seven runs of 5–10 minutes).
