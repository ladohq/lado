# M0, E14: runsc as Docker's runtime on the host against the nested runner

Date: 2026-11-27. Brief: [E14](m0-experiments-brief.md#e14-runsc-as-dockers-runtime-on-the-host);
threshold: [the plan, section 5](../session-isolation-plan.md#5-the-m0-experiments).
Machines: GitHub's hosted runners `ubuntu-24.04` (root and Docker on the VM itself), a
private repository `kao73/gvisor-spike`, branch `m0-e14`, workflow `m0.yml`. Runs
`45983021296` (all phases) and `45985489117` (isolation with additions, and the
measurements with the nested variant). Translated from the Russian report; all tables and
numbers are kept. The report refers to the raw logs in `runs/<id>/e14-X64/` (the `logs/`
files below) and to the scripts in `repo/m0/e14/` (a snapshot of the branch); **they are
not committed to this repository**.

## 1. Summary

- **The isolation is the same as in the nested runner R+net, if the host closes INPUT from
  the session bridges.** Without that rule a session reaches the host's services (ssh :22
  and anything listening on `0.0.0.0`/`::`) through its network's gateway. This holds in
  both network schemes. With the rules `iptables`/`ip6tables -I INPUT -i <session bridge> -j
  REJECT` everything is closed: processes, files, the other session, the host,
  `docker.sock`, metadata, IPv6, DNS, the internet directly. This holds for uid 1000, for
  root with Docker's default capabilities and for root with `--cap-add ALL`.
- **The install is one installer step**: download the archive and check its sha512, unpack
  it into `/usr/local/bin`, `runsc install`, `systemctl restart docker`. One catch:
  restarting dockerd (≈ 11 s) kills the containers without a restart policy. LADO's
  `compose.yaml` has `unless-stopped`, and such a container came back by itself.
- **The speed is no worse**: H (runsc on the host) and B (nested) agree within 1–4 % (H/B
  0.96–1.01×) on W2 and W7. This is a hint from a GitHub runner, not a decision.
- **Compatibility is full**: 29 of 29 checks of round 2 as uid 1000, all network through
  the proxy.
- **The component that starts the sessions holds the Docker socket, and that is root on the
  host** (shown). `default-runtime: runsc` does not protect from it: `--runtime=runc` is
  still available.
- **Decision by the threshold: the threshold is passed.** On an own server the runner uses
  the host's runtime. The nested variant is needed only where nothing can be installed on
  the host (Docker Desktop). A required condition: the INPUT rules on the host. The
  launching component is a trusted part of the host.

## 3. What was done

### 3.1 The install (`install.sh`, `logs/e14-10-install.txt`)

| step | command | what it changes |
|---|---|---|
| 1 | download the release's `gvisor.tar.bz2` and `.sha512`, `sha512sum -c` | nothing |
| 2 | `tar xjf … -C /usr/local/bin` | `runsc`, `containerd-shim-runsc-v1`, the folder `gvisor-bin/` (7 files: `gvisor_sentry`, `runsc-netgofer`, `checkpointgofer` and others), ≈ 190 MB |
| 3 | `runsc install` | creates `/etc/docker/daemon.json`: `{"runtimes":{"runsc":{"path":"/usr/local/bin/runsc"}}}`. It adds to an existing file (`-clobber` touches only this runtime). Merging into a non-empty file was not checked here: the runner had no such file |
| 4 | `systemctl restart docker` | ≈ 11 s. A container without a restart policy: `Exited (137)`; with `unless-stopped`: `Up` again |

Uninstall: remove the three paths, restore `daemon.json`, restart dockerd. The snapshots
before and after matched.

What a running session looks like on the host (`docker run --runtime=runsc`):
- containerd uses the ordinary shim `containerd-shim-runc-v2` with runsc as the binary;
- the processes `runsc-sandbox` and `runsc-gofer` run as the host's root, but in their own
  userns/mnt/pid/net, with `NoNewPrivs: 1`, `Seccomp: 2` (runsc's own filter) and a cut-down
  CapEff:
  - sentry: `chown dac_override dac_read_search fowner fsetid sys_ptrace`;
  - gofer: the same with `sys_chroot` instead of `sys_ptrace`;
- **AppArmor:** `docker inspect` says `docker-default`, but runsc's processes on the host
  are `unconfined`. runsc does not apply the container's profile to itself; the protection
  is the sandbox itself;
- `docker exec`, `logs`, `stop` (0.1 s), `start` and publishing a port on `127.0.0.1` work;
- the cgroup limits work: `--memory 256m` and allocating 600 MB give `rc=137`; with
  `--cpus 0.5`, 2 s of CPU take 4.2 s (4.0 s under runc). A side note; E8's thresholds were
  not checked here.

### 3.2 The network: two schemes

- **A**: an `--internal` network per session (10.210.N.0/24). The proxy is attached to each
  session's network.
- **B**: an ordinary bridge network per session (10.211.N.0/24), the proxy only in its own
  network `e14-egress`. Three rules in `DOCKER-USER` over the whole pool:
  - replies into 10.211/16 are allowed;
  - new connections into 10.211/16 are rejected;
  - from 10.211/16 only `proxy:3128` is allowed.
- **Hardening** for both: `iptables` and `ip6tables -I INPUT -i e14a+|e14b+ -j REJECT`, and
  `ip6tables -I FORWARD -i … -j REJECT`. `DOCKER-USER` sees only forwarded traffic; it does
  not see traffic to the host itself.

A session is a `spike-sandbox` container under `--runtime=runsc`, uid 1000. S2 listens on
`:8080` and holds a random marker. On the host:
- marker files (`/root`, mode 600, and `/tmp`, mode 644);
- a marker process;
- services on `127.0.0.1:9999`, `0.0.0.0:9998`, `[::]:9997`, plus ssh on `:22`.

TCP targets: every address of the host (eth0, docker0, the bridges), every listening port
of the host, and 2375/2376: 42 pairs in all. IPv6: the link-local address of each host
interface, taken after S1 is started. S1 is created anew before each probe run.

### 3.3 The isolation table (run 2, `logs/e14-21-iso.md`)

`u1000` is uid 1000. `u0` is root with Docker's default capabilities (in 28.0.4 without
`NET_RAW`/`NET_ADMIN`; *note added in translation: wrong about `NET_RAW`, see
[E9](m0-e9.md), section 4: a runc container gets it, runsc drops it itself*). `u0all` is root in a container with `--cap-add ALL`.

| attempt from S1 | A, no hardening | B, no hardening | A, hardening (u1000/u0/u0all) | B, hardening (u1000/u0/u0all) |
|---|---|---|---|---|
| processes of S2 and the host (`ps`, `/proc/*/cmdline`) | closed | closed | closed | closed |
| files and marker strings of S2 and the host | closed | closed | closed | closed |
| `docker.sock`, host paths in mountinfo, DMI | closed | closed | closed | closed |
| TCP to S2 directly | closed | closed | closed | closed |
| **the host's services, IPv4** | **open**: the own network's gateway `10.210.1.1` :22, :9997, :9998 | **open**: all 5 host addresses :22, :9997, :9998 | closed | closed |
| the host's services, IPv6 link-local | closed | closed | closed | closed |
| IPv6 out | closed | closed | closed | closed |
| metadata `169.254.169.254` (answers from the host) | closed | closed | closed | closed |
| the internet directly, DNS to 8.8.8.8 | closed | closed | closed | closed |
| DNS of external names (a leak channel) | closed | closed | closed | closed |
| the proxy's other ports | closed | closed | closed | closed |
| the proxy reachable, example.com through the proxy | ok | ok | ok | ok |
| root: a default route through the gateway or the proxy, then out | closed | closed | closed | closed |
| the host's rules after the attempts | unchanged | unchanged | unchanged | unchanged |
| *through the proxy to S2* | *reaches it* | *no* | *reaches it* | *no* |
| *through the proxy to a host service* | *reaches it* | *reaches it* | *reaches it* | *reaches it* |

The rows in italics are about a proxy without an allowlist; that is E3's subject. It matters
for the choice of scheme: **in A the proxy becomes a bridge between sessions**, because it
is attached to all their networks. B does not have this.

What is seen from inside:
- the session has no IPv6 address (except `::1`) and no IPv6 route: the Docker network has
  no IPv6;
- `iptables` does not work inside (`Failed to initialize nft`);
- `ip route`/`ip addr` without `NET_ADMIN` give `Operation not permitted`;
- with `ALL` the route changes, but still does not get out;
- raw and packet sockets are refused even with `ALL`;
- `mount tmpfs` with `ALL` succeeds, but inside the sandbox;
- `/proc/sysrq-trigger` gives EIO, `core_pattern` does not exist;
- `/proc/kcore`, DMI and `/sys/class/net` do not exist, the CPU model is `unknown`.

**Docker's DNS (`127.0.0.11`) does not work under runsc at all:**
- a comparison on the same networks:
  - runc in A resolves `e14-proxy`;
  - runc in B resolves `example.com` too: a DNS leak channel of an ordinary container;
  - runsc in A and B resolves nothing;
- for isolation this is a plus: no leak through DNS;
- but the session must reach the proxy by IP, not by the container's name.

### 3.6 Who holds the Docker socket (`logs/e14-50-sock.txt`)

In this design the socket is needed by the component that starts the session containers. A
"launcher" container with `docker.sock` mounted can:
1. do what is intended: `docker run --runtime=runsc` (gVisor);
2. `docker run --runtime=runc --privileged --pid=host -v /:/host`. The result: the host's
   root, reading `/etc/shadow` (1098 bytes), `nsenter -t 1` into the host's namespaces (the
   host's `hostname`);
3. see and touch every container of the host, LADO itself included.

After `"default-runtime": "runsc"` a container without `--runtime` lands in gVisor. But
`--runtime=runc` still gives an ordinary container. So only a narrow API of the launching
component, or a Docker authz plugin, can limit this, not the runtime setting.

## 4. What it means for the plan

A proposal for the supervisor:
- **E14's threshold is passed.** On an own server (M5a, step 2) the runner is a component
  on the host that runs `docker run --runtime=runsc` per session. The nested R+net with its
  own seccomp and six capabilities stays only for Docker Desktop (macOS, Windows) and hosts
  where nothing can be installed.
- **The installer and `lado doctor`** get:
  - the runsc install (the 4 steps above);
  - **the INPUT rules for the session bridges (iptables and ip6tables)**; without them there
    is a hole to the host's services;
  - their check in `lado doctor`;
  - a subnet pool and a bridge name prefix (`com.docker.network.bridge.name`), so the rules
    are static, not per session.
  The rules in `INPUT`/`DOCKER-USER` do not survive a reboot by themselves; the launching
  component must install them at its start.
- **The network scheme: B** (a bridge network per session, the proxy in a separate network,
  `DOCKER-USER` rules over the pool). In A the proxy becomes a bridge between sessions. In
  both schemes a proxy without an allowlist reaches the host's services, so E3's address
  check before connecting is required whatever the choice.
- **The launching component is a trusted part of the host** (root through the socket). Its
  API must be narrow: "start session X" with fixed parameters (runsc, its own network, no
  `--privileged`, no arbitrary binds). It must not be handed to an untrusted party; this is
  already in the threshold.
- Reach the proxy by IP: Docker's DNS does not work under runsc. This also means there is
  no DNS leak.
- Threat model row T5 for M5a rests on gVisor alone. AppArmor does not apply to runsc's
  processes.

## 5. Problems and surprises; what was not done

- Run 1: B wrote no rows in the measurements, and root in R+net without `DAC_OVERRIDE` could
  not write to `/work`. Fixed and repeated in run 2 together with the measurements of A and
  H.
- In run 1 the IPv6 targets were collected before S1 was started, and the link-local
  address of B's bridge (the interface was DOWN then) did not make the list. In run 2 the
  targets are taken after S1 is started. The result is the same: the container has no IPv6
  but `::1`.
- The `INPUT REJECT` rule has no exceptions: a session in this design needs neither Docker's
  DNS nor anything on the host. If the runner needs a service on the host (the Agent API
  gateway), that will be one explicit exception by port.
- Not done:
  - arm64 (the install steps differ only by the URL);
  - `runsc install` merging into a non-empty `daemon.json`;
  - Docker 29 and other environments (that is E7);
  - speed on a dedicated server (that is E1 and "E14's speed" in the plan);
  - `--runtime=runsc` with a bind-mounted repository (measured only on the container's
    disk).
- Metadata through the proxy was not really checked: `proxy.py` does not pass the
  `Metadata` header, and Azure answers with an error. That is E3.
