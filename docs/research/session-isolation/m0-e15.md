## 1. Summary

- **The threshold is passed: ptrace between sandboxes is closed and the network works → a
  candidate profile instead of R+net.**
- **A runner without SYS_ADMIN.** Root in the runner with three capabilities: `SETUID`,
  `SETGID`, `NET_ADMIN` (R+net had six: also `SYS_ADMIN`, `NET_RAW`, `SETFCAP`). Plus
  `no-new-privileges`, seccomp "Docker default + 8 calls" and AppArmor `lado-runner-lite`.
- **Sandboxes under different host uids.** Each runs under its own uid (2001, 2002), in its
  own user namespace (`0 → N`, one line) and its own netns. runsc runs as `--rootless
  --network=host` inside that netns.
- **Access between sandboxes is closed in every check.** A process with one sandbox's uid
  (the model of an escape from its sentry) cannot get at the processes of another: a
  signal, `PTRACE_ATTACH`, `/proc/<pid>/mem`, `environ`, `root`, `fd`. The same for the
  proxy (uid 65534) and the runner's root. The runsc state folders, the bundles and `/work`
  of another sandbox cannot be listed. The result is the same with `yama.ptrace_scope=1` and
  with `0`: what holds is the uid separation, not yama. The baseline on its own processes
  passes (8 of 8), so the check is working.
- **Network: 0 holes in the 54 rows** of E3's network probe, as uid 1000 and as root in the
  sandbox. The runner's rules did not change after the probes. Round 2's smoke check: the
  sandbox starts, `git status`, tmux, curl through the proxy pass, the direct way out is
  closed.
- **Ubuntu 24.04, `apparmor_restrict_unprivileged_userns=1`.** The restriction works: under
  `unconfined` no user namespace is created. The runner's profile with the rule `userns,`
  (`lado-runner-lite`) lifts it; the host's sysctl need not change.
- **Two costs.**
  - Rootless runsc cannot do gVisor's own network: it refuses `--network=sandbox`. What is
    left is `--network=host`, that is the host kernel's TCP stack (inside the sandbox's
    netns), not gVisor's netstack. The kernel's network surface is larger than in R+net.
  - **`codex sandbox` (bwrap) as root in the sandbox does not work**: the sandbox's root has
    no `CAP_SETUID`, writing `uid_map` is refused. As uid 1000 a user namespace inside is
    created. But `codex sandbox` itself failed further on, in its helper
    `codex-linux-sandbox`; this was not finished (section 5).

## 3. What was done

### 3.1 The design

Inside the runner (`rl-in.sh`), for each sandbox `sI` with uid `N`:

1. **The namespace holder.** The runner's root starts
   `setpriv --reuid N --regid N --clear-groups -- unshare -U -r -n sleep infinity`. This
   gives a user namespace with `uid_map 0 N 1` and an empty netns; both are owned by uid N.
2. **veth.** The runner's root (`NET_ADMIN`) creates the pair `veth-sI`/`e15pI` and moves
   one end into the holder's netns. The address `10.215.I.1/24` is on the runner's side.
3. **The address inside.** uid N, through `nsenter -t H -U -n --preserve-credentials` (root
   of its own userns), renames the end to `eth0`, sets `10.215.I.2/24` and the default
   route.
4. **The sandbox.** uid N runs `runsc --rootless --network=host --ignore-cgroups
   --root=/run/e15/N run -bundle /bundles/sI -detach sI` in the same namespaces. In the
   sandbox the process is uid 0 or 1000.

The preparation (the bundle, the rootfs, `chown N` and `chmod 700` for `/bundles/sI`,
`/run/e15/N`, `/work/sI`) is done by a privileged `docker exec`. This models the control
layer, as in round 2.

The network rules and the proxy are as in E3 (inside the runner):

- `FORWARD -i veth+ REJECT`;
- `INPUT` from `veth+`: only established connections and the ports 3128 (the proxy) and 7000
  (the gateway), the rest REJECT;
- `ip6tables` INPUT and FORWARD REJECT from `veth+`;
- `strict_proxy.py` as uid 65534 with `-m owner` rules (no private or loopback addresses,
  except `127.0.0.11`).

Decoys: services on 127.0.0.1:9999, 0.0.0.0:9998, [::]:9997.

### 3.2 What was looked at

- **`crossuid.py`** runs as uid 2001, then as 2002 (through `setpriv`, without
  capabilities, `NoNewPrivs=1`). For each process of each target (its own sandbox as the
  baseline, the other sandbox, the proxy, the runner's root) it tries:
  - `kill 0`;
  - `PTRACE_ATTACH`;
  - reading `/proc/<pid>/mem` and `environ`;
  - listing `/proc/<pid>/root` and `fd`.

  Then listing `/run/e15/<other uid>`, `/bundles/<other>`, `/work/<other>`. All of it twice:
  with yama 1 (as on the host) and with yama 0 (yama set back to 1 after the probes).
- **Round 2's smoke check** (`smoke-inner.sh`) in both sandboxes.
- **E3's network probe** (`e3probe.py`, 54 rows) from s1 as uid 1000 and as uid 0; a
  comparison of `iptables -S` and `ip6tables -S` before and after.
- **Variants**: one start of s1 per single change, to find what of the profile is really
  needed.

### 3.4 Access between sandboxes (`logs/e15-21-cross.md`)

| what | s1 → s2, s2 → s1 (yama 1 and 0) | → the proxy (65534) | → the runner's root |
|---|---|---|---|
| a signal | closed (EPERM) | closed (EPERM) | closed |
| `PTRACE_ATTACH` | closed (EPERM) | closed (EPERM) | closed |
| `/proc/pid/mem` | closed (EACCES) | closed (EACCES) | closed |
| `/proc/pid/environ` | closed (EACCES) | closed (EACCES) | closed |
| `/proc/pid/root`, `fd` | closed (EACCES) | closed (EACCES) | closed |
| `/run/e15/<uid>`, the bundle, `/work` | closed (EACCES) | | |
| **its own sandbox (the baseline)** | signal, ptrace, environ, root, fd: 8 of 8; mem opens (EIO at offset 0) | | |

In round 2 the profile R (rootless with a shared uid) was dropped precisely because one
sandbox's sentry could trace another's. Here that path is closed by the kernel at the uid
level. AppArmor `lado-runner-lite` allows ptrace between its own processes, and so does yama
0: the ban rests only on the different uids.

### 3.5 Network (`logs/e15-31-net.md`)

As uid 1000 and as root in s1, the same, **0 open**:

- closed:
  - direct TCP to the runner's and the host's ports;
  - IPv6 link-local to the runner, IPv6 out;
  - metadata directly and through the proxy (CONNECT, GET, the name
    `169-254-169-254.nip.io`);
  - the internet directly and DNS directly;
  - the proxy resolving a name outside the allowlist;
- all CONNECTs to localhost in any notation, to the runner's and the host's addresses, to
  the other sandbox S2 (by address and by a `nip.io` name), to allowed names with private
  addresses, IP literals, ports 80 and 22;
- 16 parsing checks (smuggling, NUL, LF, 100 KB, 1 MB, 5000 headers, pipelining): refused,
  the proxy alive.

Open is what should be: the gateway port (7000) and an allowed name through the proxy
(`example.com:443`, in the proxy's log `allow … -> 104.20.23.154`).

As in E3: 300 held connections exhaust the proxy (`503` for an allowed request). A
per-client limit is needed.

### 3.6 Smoke

| check | s1 and s2, uid 0 | s1, uid 1000, `HOME=/home/agent` |
|---|---|---|
| the sandbox starts (`uname`: `4.19.0-gvisor`) | yes | yes |
| `git status` | PASS | PASS |
| tmux `send-keys` + `capture` | PASS | PASS |
| curl through the proxy | PASS (200) | PASS (200) |
| the direct way out (1.1.1.1, DNS) | closed | closed |
| `codex sandbox -- true` | **FAIL**: `bwrap: setting up uid map: Operation not permitted` | **FAIL**: `could not create PATH aliases: Permission denied`, then `bwrap: execvp codex-linux-sandbox: No such file or directory` |

Why bwrap fails for root (run `46051392027`):

| in s1 | uid 0 | uid 1000 |
|---|---|---|
| `uid_map` (gVisor's view) | `0 0 4294967295` | `0 0 4294967295` |
| CapEff / CapBnd | `20000420` / `20000420` (KILL, NET_BIND_SERVICE, AUDIT_WRITE) | `0` / `20000420` |
| `unshare -Ur id` | `write failed /proc/self/uid_map: Operation not permitted` | `uid=0(root)` |
| `unshare -U --map-current-user` | the same | `uid=1000(agent)` |
| `bwrap --unshare-user` | `setting up uid map: Operation not permitted` | rc=0 |
| `bwrap --unshare-user --uid 0` | the same | `uid=0(root)` |

The sandbox's root owns only `0 → 0`. To write the map gVisor requires `CAP_SETUID`, and the
default spec does not have it. An ordinary user writes a map "onto itself" without
capabilities. In R+net ([E9](m0-e9.md), rootful runsc) `codex sandbox` passed.

## 4. What it means for the plan

- **A candidate profile "R-uid" instead of R+net:**

  | | R+net | R-uid (E15) |
  |---|---|---|
  | the capabilities of the runner's root | SYS_ADMIN, NET_ADMIN, NET_RAW, SETUID, SETGID, SETFCAP | SETUID, SETGID, NET_ADMIN |
  | seccomp | `runner.json` | Docker default + clone, clone3, unshare, setns, mount, umount2, pivot_root, chroot |
  | AppArmor | `lado-runner-lite` | `lado-runner-lite` (with `userns,`) |
  | the sandboxes' uid on the host | shared (root) | its own for each (2001, 2002, …) |
  | runsc | rootful, `--network=sandbox` | `--rootless --network=host` in the holder's netns |
  | ptrace between sentries | not checked in E15 | closed by the kernel: different uids |

- **What changes in the control layer:**
  - a uid handed out per session (a range, for example 2001+; one uid, one sandbox; reuse
    only after a full stop);
  - per sandbox: a `unshare -U -r -n` holder, a veth from the runner's root, the address
    through `nsenter`;
  - the bundle, runsc's state and `/work` belong to the sandbox's uid with mode 700;
  - stopping is done as that uid (the runner's root has no `CAP_KILL`, as in E3).
- **Cost 1: the network through the host's kernel.** In R-uid the sandbox's TCP/IP goes
  through the kernel's stack (in its netns), not through gVisor's netstack. The limits are
  the same (the runner's iptables, the proxy), and E3's network probe found no holes. But a
  vulnerability in the kernel's network stack gets closer. If that is unacceptable, there is
  `--network=none` with a channel to the proxy over a unix socket; that is a separate
  experiment.
- **Cost 2: agents running as root inside the sandbox lose bwrap.** So the agents must run
  as an unprivileged user (uid 1000). That is right anyway. As uid 1000 a user namespace
  inside is created. `codex sandbox` in this mode is not finished yet; check it together
  with E10 (its own HOME and installing codex for a second user).
- **Ubuntu 24.04:** the host's sysctl is not touched; only the runner's AppArmor profile with
  `userns,` is needed. `docker-default` does not fit: runsc does not start under it.
- **The link with E14, E3:** E14's network rules (INPUT, ip6tables) and E3's strict proxy
  with owner rules carry over unchanged; inside the runner they work the same.

## 5. Problems and surprises; what was not done

- **Run `46032164575`:** `nsenter: setgroups failed`. In the holder's userns `setgroups` is
  refused (`unshare -r` writes `deny`). Fixed with the flag `--preserve-credentials`.
- **Run `46035718372`:**
  - `cd /bundles/sI: Permission denied`: the runner's root has no `DAC_OVERRIDE`, and the
    700 folder belongs to the sandbox's uid. Fixed: `run -bundle` instead of `cd`.
  - The second uid in the cross check was computed wrong (`3003-me`). Fixed to `4003-me`.
- **Run `46039732118` hung for more than an hour:** the output of `runsc run -detach` was
  caught through `$(...)`, and the detached sandbox inherited that pipe and kept it open.
  The run was cancelled (no logs). Fixed: the output goes to a file, the holder is detached
  from stdout, each call in the runner has a `timeout`, and each phase 40 minutes.
- **`codex sandbox` as uid 1000 is not finished.** With `HOME=/home/agent` bwrap passes, but
  codex writes `could not create PATH aliases: Permission denied` and does not find
  `codex-linux-sandbox`. It looks like codex's install (the helper is installed into a
  folder the second user cannot write to), not isolation. The three variants for this step
  were used up, so I stopped. Moved to E10.
- **The escape model.** `crossuid.py` ran as a plain uid without capabilities, not from a
  real sentry. A real sentry has capabilities in its own userns. By the kernel's rules they
  do not act over a neighbouring userns with another owner, but with the capabilities of its
  own userns this was not checked separately.
- **Not checked:**
  - how the runner's root (without `SYS_PTRACE`, without `CAP_KILL`) sees the sandboxes'
    processes: it is the control layer and was not attacked separately;
  - whether each of the eight added seccomp calls is needed;
  - speed (E14 measured only R+net).
- **Time:** about 4 hours instead of 1–2, of which an hour was the hung run.
