# R4: Credentials, terms of service, secrets and remote-running capabilities of agent CLIs for LADO cloud mode

Research date: 2026-10-18. Every claim has a source URL. Quotes are verbatim from the fetched page
unless marked "(secondary)". This is research, not legal advice: the paid-service questions in §2
need a lawyer and, for Anthropic and OpenAI, written confirmation from the vendor.

## 0. LADO today (context)

- `src/lado/providers/claude.py` already treats `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY`,
  `ANTHROPIC_AUTH_TOKEN` as "logins without the keychain", and on macOS hints at
  `claude setup-token` when the keychain login is unreachable.
- `docker/Dockerfile` and `docker/compose.yaml` pass `CLAUDE_CODE_OAUTH_TOKEN`, `GH_TOKEN`,
  `OPENAI_API_KEY`, kit keys (e.g. `YOUGILE_API_KEY`) as files in `secrets/`, or let the user log in
  inside the container (`claude`, `codex login`, `opencode auth login`, `kilo auth login`) with the
  login kept on the home volume; git over https uses `gh auth git-credential`, ssh uses a forwarded
  agent socket.
- Agents run inside tmux panes (a pty), so "no TTY" is not a constraint for LADO's own mode of
  running; it matters only if cloud mode switches to headless `-p`/`exec`/`run` or ACP.
- All secrets today sit in the agent's environment or home, i.e. inside the agent's reach.

## 1. Authentication per CLI

### 1.1 Claude Code

Methods and precedence (https://code.claude.com/docs/en/authentication):
1. Cloud provider when `CLAUDE_CODE_USE_BEDROCK` / `_VERTEX` / `_FOUNDRY` is set.
2. `ANTHROPIC_AUTH_TOKEN` (sent as `Authorization: Bearer`, "Use this when routing through an LLM
   gateway or proxy").
3. `ANTHROPIC_API_KEY` (`X-Api-Key`; "In non-interactive mode (`-p`), the key is always used when
   present"; interactively it asks once to approve).
4. `apiKeyHelper` script output, "for dynamic or rotating credentials, such as short-lived tokens
   fetched from a vault".
5. `CLAUDE_CODE_OAUTH_TOKEN`, "A long-lived OAuth token generated by `claude setup-token`. Use this
   for CI pipelines and scripts where browser login isn't available."
6. Anthropic profile / Workload Identity Federation credentials (`ANTHROPIC_PROFILE`,
   `ANTHROPIC_FEDERATION_RULE_ID` + `ANTHROPIC_ORGANIZATION_ID`, `ANTHROPIC_IDENTITY_TOKEN_FILE`).
7. Subscription OAuth from `/login` (Pro, Max, Team, Enterprise).
Plus a self-hosted "Claude apps gateway" with corporate SSO, which outranks all of them.

- **setup-token**: "generate a one-year OAuth token with `claude setup-token` ... It does not save
  the token anywhere ... This token authenticates with your Claude subscription and requires a Pro,
  Max, Team, or Enterprise plan. It can only make model requests, so it can't establish Remote
  Control sessions or fetch claude.ai connectors. MCP servers you configure locally still work."
  `--bare` mode does not read it. (same page)
- **Headless login in a container**: "If your browser shows a login code instead of redirecting
  back ... paste it into the terminal ... common in WSL2, SSH sessions, and containers." (same page)
- **Storage**: Linux `~/.claude/.credentials.json` mode 0600; macOS Keychain (falls back to the file
  when the keychain is locked, e.g. over SSH); `CLAUDE_CONFIG_DIR` relocates it (same page).
- **Refresh**: a `/login` credential refreshes itself; near expiry it warns "Your login expires in 3
  days"; once it cannot refresh, "each model request fails with `Login expired · Please run
  /login`"; unattended sessions "stop making progress once the credential expires" (same page).
  The setup-token is static for a year, so no refresh race.
- **Sharing one login across many containers**: no explicit statement. Practical reading: the
  setup-token is a static bearer and can be set in many containers; a `/login` credential file
  refreshes and rewrites itself, so copying it to several containers risks refresh races (the same
  failure OpenAI documents for Codex, §1.2). All parallel use counts against one plan's limits, and
  "Advertised usage limits for Pro and Max plans assume ordinary, individual usage of Claude Code
  and the Agent SDK" (https://code.claude.com/docs/en/legal-and-compliance).
- **Cloud routes**: Bedrock, Google Cloud Agent Platform (Vertex), Microsoft Foundry, "Claude
  Platform on AWS"; managed `allowedProviders` can pin which ones a machine may use (same auth page).
- **Gateways (LiteLLM, OpenRouter, own proxy)**: `ANTHROPIC_BASE_URL` + `ANTHROPIC_AUTH_TOKEN`
  (bearer) (https://code.claude.com/docs/en/authentication, https://code.claude.com/docs/en/llm-gateway).
- **Workload Identity Federation (best fit for k8s)**: "workloads authenticate to the Claude API with
  short-lived OpenID Connect (OIDC) tokens instead of long-lived `sk-ant-...` API keys", supports
  "Kubernetes ... projected service-account tokens", token lifetime 60–86400 s (default 3600, wizard
  600), the SDK re-reads `ANTHROPIC_IDENTITY_TOKEN_FILE` on every exchange; JWTs with `jti` are
  single-use by default (https://platform.claude.com/docs/en/manage-claude/workload-identity-federation).
  Claude Code ranks federation credentials at step 6 above. API billing only (no subscription).
- **Anthropic's own cloud/self-hosted runner** (competitor and reference design): "Self-hosted
  environments are in public beta on Team and Enterprise plans"; runner on your infra, control plane
  at Anthropic; "the session authenticates with an Anthropic-issued, session-scoped OAuth token";
  a runner "locks to that owner when it claims its first session"
  (https://code.claude.com/docs/en/self-hosted-environments).

### 1.2 OpenAI Codex CLI

(https://developers.openai.com/codex/auth redirects to https://learn.chatgpt.com/docs/auth)
- **Methods**: "Sign in with ChatGPT for subscription access"; "Sign in with an API key for
  usage-based access"; Enterprise "Codex access tokens" ("Use an access token when automation needs
  ChatGPT workspace access"; "intended for trusted scripts, schedulers, and private CI runners");
  custom `model_providers` with `env_key` (gateways, Azure, OpenRouter, LiteLLM).
- **Headless**: device code login (beta) `codex login --device-auth`, must be enabled in ChatGPT
  security settings or by the workspace admin; fallback "copy `~/.codex/auth.json` to the headless
  machine, or forward the localhost callback over SSH".
- **Storage**: `cli_auth_credentials_store` = `file` (`auth.json` under `CODEX_HOME`), `keyring`,
  `auto`, or `ephemeral` ("keeps credentials in memory only for the current process"). Admins can
  enforce it.
- **Refresh**: "Codex refreshes tokens automatically during use before they expire." In CI, "when
  `last_refresh` is older than about 8 days, Codex refreshes the token bundle" and writes it back,
  so the file must be persisted (https://learn.chatgpt.com/docs/auth/ci-cd-auth).
- **Sharing across containers: explicitly no.** "Do not share the same file across concurrent jobs
  or multiple machines." Reseeding may be needed if "another machine or concurrent job rotated the
  token first." "Do not use this workflow for public or open-source repositories." For CI, "API
  keys are still the recommended default for automation." (https://learn.chatgpt.com/docs/auth/ci-cd-auth,
  https://learn.chatgpt.com/docs/auth)
- **Consequence for LADO**: one ChatGPT login per container (each logs in with device auth), or an
  API key / Enterprise access token for fleets. The LADO Docker image's "log in once inside and
  keep it on the home volume" is fine for one container, not for N replicas sharing a volume.

### 1.3 Kilo CLI (Kilo Code; acquired by Anaconda, July 2026)

- `kilo auth list | login [url] | logout`, `/connect` in the TUI; login (OAuth) for OAuth-capable
  providers (Kilo account, GitHub Copilot); API keys via env and `{env:VAR}` in config
  (https://kilo.ai/docs/code-with-ai/platforms/cli-reference, https://kilo.ai/docs/code-with-ai/platforms/cli).
- Env mapping: "`KILO_<FIELD_NAME>` (e.g., `KILO_API_KEY` → `apiKey`)", `KILO_PROVIDER`,
  `KILO_ORG_ID` ("Best for non-interactive and CI environments"); `{env:...}` references "only work
  in trusted config" (https://kilo.ai/docs/code-with-ai/platforms/cli).
- Headless: `kilo run --auto "..."`; without `--auto` a non-interactive run "auto-rejects any
  permission request it receives"; exit 124 = timeout (same page).
- Storage: provider auth in `auth.json` under the data dir, mode 0600, per the CLI runtime
  architecture doc (https://kilo.ai/docs/contributing/architecture/cli-runtime) (secondary summary;
  third-party guides cite `~/.local/share/kilo/auth.json`).
- Kilo Gateway: an OpenAI-compatible endpoint with one key for many models; pay-as-you-go plus
  "Kilo Pass" credits (secondary: https://coder.com/docs/ai-coder/ai-gateway/clients/kilo-code,
  https://rywalker.com/research/kilo).
- Ownership: Anaconda acquired Kilo Code, announced 2026-07-15
  (https://www.fenwick.com/insights/experience/fenwick-represents-anaconda-acquisition-kilo-code,
  https://byteiota.com/anaconda-bought-kilo-code-what-happens-to-your-setup/). Kilo's terms now
  mention Anaconda artefacts (§2.4).

### 1.4 OpenCode

(https://opencode.ai/docs/providers/)
- `/connect` stores keys in `~/.local/share/opencode/auth.json`; providers can read env vars and
  `{env:VAR}` / `{file:path}` substitution in `opencode.json`.
- OpenAI: "ChatGPT Plus/Pro" browser login or API key. OpenCode is a launch partner of OpenAI's
  "Sign in with ChatGPT" plan usage (secondary:
  https://www.developersdigest.tech/blog/sign-in-with-chatgpt-coding-agents-plan-usage-2026).
- Anthropic: the docs still show a Claude Pro/Max option, but also say "There are plugins that allow
  you to use your Claude Pro/Max models with OpenCode. Anthropic explicitly prohibits this", and the
  bundled plugins were removed as of 1.3.0. The Register reports that OpenCode removed Claude Pro/Max
  support citing "anthropic legal requests"
  (https://www.theregister.com/software/2026/02/20/anthropic-clarifies-ban-on-third-party-tool-access-to-claude/5014546).
- Bedrock (`AWS_PROFILE`, keys, `AWS_BEARER_TOKEN_BEDROCK`), Vertex (`GOOGLE_APPLICATION_CREDENTIALS`),
  Azure (key or Entra ID via `az login`), OpenRouter (key), any OpenAI-compatible endpoint
  (`@ai-sdk/openai-compatible` + `baseURL`; LiteLLM fits here).
- OpenCode Zen (curated models, pay per use) and Go (low-cost subscription) via an OpenCode API key.

### 1.5 Others

- **Gemini CLI**: Google account (Code Assist), `GEMINI_API_KEY`, Vertex. Terms page: "Directly
  accessing the services powering Gemini CLI (for example, the Gemini Code Assist service) using
  third-party software, tools, or services (for example, using OpenClaw with Gemini CLI OAuth) is a

  (https://geminicli.com/docs/resources/tos-privacy/). Reports say that from 2026-06-18 Google stopped

- **GitHub Copilot CLI**: headless via an env token; fine-grained PAT (`github_pat_`, "Copilot
  Requests" permission, owned by a personal account), OAuth `gho_`, GitHub App user tokens `ghu_`;
  classic PATs unsupported; Actions' `GITHUB_TOKEN` has no Copilot permission
  (https://docs.github.com/en/copilot/how-tos/copilot-cli/set-up-copilot-cli/authenticate-copilot-cli,
  https://docs.github.com/en/enterprise-cloud@latest/copilot/how-tos/copilot-cli/set-up-copilot-cli/troubleshoot-copilot-cli-auth).
  Lookup order `COPILOT_GITHUB_TOKEN`, `GH_TOKEN`, `GITHUB_TOKEN` (secondary, unverified). Billing is
  per Copilot seat; one human's seat per token.
- **ACP agents**: auth stays the agent's own; ACP only carries the session (see §4.3).

## 2. Terms of service

Scenarios: **(a)** a user runs their own subscription in their own VM/container (LADO self-hosted
cloud mode); **(b)** a third-party service (LADO's operator) runs agents with the user's subscription
credentials; **(c)** a hosted service uses its own API keys and charges users (resale).

### 2.1 Anthropic / Claude Code — the most explicit and the strictest

Key text, https://code.claude.com/docs/en/legal-and-compliance:

> "Unless we've mutually agreed otherwise, preinstalling or running Claude Code in your products or
> services (e.g. in hosted sandboxes or other agent infrastructure) requires agreeing to our
> Commercial Terms of Service and complying with the conditions below:
> **The Claude Code binary must not be modified.** ... customers may not remove, disable, or restrict
> any authentication method built into it (including methods that permit signing in with a Claude
> account or the user's own API key).
> **Customers may not pay for, resell, or intermediate Claude usage on their end users' behalf.** Each
> end user must authenticate with their own Anthropic API key, Claude subscription plan credentials,
> or 3P inference provider credential (Amazon Bedrock, Google Cloud's Agent Platform, Microsoft
> Foundry). That usage is billed directly to the end user under their own agreement with Anthropic
> or, for third-party inference providers, with the applicable provider."

> "**OAuth authentication** is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and
> Enterprise subscription plans and is designed to support ordinary use of Claude Code and other
> native Anthropic applications."
> "**Developers** building products or services that interact with Claude's capabilities, including
> those using the Agent SDK, should use API key authentication through Claude Console or a supported
> cloud provider. Anthropic does not permit third-party developers to offer Claude.ai login into their
> own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their
> users. Moreover, developers may not collect, store, or intermediate Claude.ai credentials or session
> tokens — sign-in to a Claude account must complete through Anthropic's own flow."
> "This does not restrict how customers provision and manage their own API keys ... for use by the
> customer's own authorized users ... provided the resulting usage is billed to the key owner ... and is
> not resold or intermediated as described above. Nor does it prevent an end user from signing in to
> the unmodified Claude Code binary with their own Claude subscription, including where a platform
> hosts Claude Code as described under *Can customers offer Claude Code in their products?* above."
> "Anthropic reserves the right to take measures to enforce these restrictions and may do so without
> prior notice."

Consumer Terms (effective 2025-10-08, https://www.anthropic.com/legal/consumer-terms): §3 item 7
forbids, "Except when you are accessing our Services via an Anthropic API Key or where we otherwise
explicitly permit it, to access the Services through automated or non-human means, whether through a
bot, script, or otherwise"; §2: "You may not share your Account login information, Anthropic API key,
or Account credentials with anyone else" nor "make your Account available to anyone else".

Commercial Terms (effective 2025-06-17, https://www.anthropic.com/legal/commercial-terms): A.1
allows using the Services "to power products and services Customer makes available to its own
customers and end users"; D.4(a) forbids to "resell the Services except as expressly approved by
Anthropic"; D.5 "Customer is responsible for all activity under its account."

Enforcement history: Anthropic engineer Thariq Shihipar: "Third-party harnesses using Claude
subscriptions create problems for users and are prohibited by our Terms of Service"; compliance page
updated week of 2026-02-20; OpenCode dropped Claude login after "anthropic legal requests"
(https://www.theregister.com/software/2026/02/20/anthropic-clarifies-ban-on-third-party-tool-access-to-claude/5014546;
secondary: https://winbuzzer.com/2026/02/19/anthropic-bans-claude-subscription-oauth-in-third-party-apps-xcxwbn/).

Reading for LADO:
- **(a) Allowed, with a caveat.** LADO runs the *unmodified* `claude` binary, and the user signs in
  through Anthropic's flow or uses `claude setup-token`, which Anthropic documents for "CI pipelines
  and scripts" — that is the "explicitly permit" exception to Consumer Terms §3.7. Caveats: usage
  limits "assume ordinary, individual usage", so a fleet of parallel agents on one Pro/Max plan can
  hit limits and invites scrutiny; Team/Enterprise or API keys are cleaner for heavy fleets.
- **(b) Allowed only in a narrow shape, and risky.** The page explicitly allows "a platform [that]
  hosts Claude Code" where the end user signs in to the unmodified binary with their own subscription.
  But the operator must (1) accept the Commercial Terms, (2) not modify the binary or hide its login
  methods, (3) not "collect, store, or intermediate Claude.ai credentials or session tokens", sign-in
  must complete "through Anthropic's own flow". A UI field "paste your `CLAUDE_CODE_OAUTH_TOKEN`"
  that LADO stores in its secret store is plausibly "collect, store" — **do not build that for the
  hosted offering**. Safer shape: the user runs `/login` (paste-code flow) inside their own container
  in LADO's UI terminal, and the credential lives only on that user's volume. Even then, the
  operator's infrastructure holds the credential file at rest; whether that counts as "store" is not
  defined. Get written confirmation from Anthropic (the page says "contact sales").
  Users' own Anthropic API keys or their own Bedrock/Vertex/Foundry credentials are explicitly fine.
- **(c) Prohibited for Claude Code** unless "mutually agreed otherwise": "Customers may not pay for,
  resell, or intermediate Claude usage on their end users' behalf." This is a **hard blocker** for a
  LADO-hosted "we pay Anthropic, you pay us" plan with Claude Code agents. (Building one's own agent
  on the Messages API / Agent SDK with the operator's own key is a different product, governed by
  Commercial Terms A.1 vs D.4(a); still needs care, since D.4(a) bars reselling "the Services".)
- Branding: may say "runs Claude Code" in plain text, may not use the name/logo in the product name
  (same legal page).

- **(c) Plausibly allowed with API keys** under the Services Agreement (Customer Application for End

## 3. Secret handling patterns for cloud agents

### 3.1 Injection
- k8s Secrets as env vars or mounted files; prefer files (no leakage via `/proc/*/environ`, `env`
  dumps, child processes) and a secret store CSI driver (Vault, AWS/GCP/Azure secret managers).
  LADO's compose already uses files in `secrets/`.
- Short-lived instead of static where the vendor supports it:
  - Anthropic: Workload Identity Federation from Kubernetes projected service-account tokens, tokens
    of minutes (https://platform.claude.com/docs/en/manage-claude/workload-identity-federation);
    Claude Code's `apiKeyHelper` for "short-lived tokens fetched from a vault"
    (https://code.claude.com/docs/en/authentication).
  - OpenAI: Enterprise Codex access tokens; `cli_auth_credentials_store = "ephemeral"`
    (https://learn.chatgpt.com/docs/auth).
  - Clouds: Bedrock/Vertex/Azure via IRSA / GKE Workload Identity / Entra Workload ID, no static keys.
- One credential per container for refreshing logins (Codex: explicit; Claude `/login`: same risk).

### 3.2 Keep secrets out of the agent's reach (egress proxy that injects the key)
- Pattern: the agent container holds no real secret (or an opaque placeholder); a sidecar or host
  proxy terminates TLS (its own CA trusted in the container), matches host/path, injects the real
  header, and enforces a default-deny egress allowlist.
  - Anthropic's own cloud sessions: "git credentials and signing keys stay outside the sandbox, and a
    proxy authenticates on the session's behalf with scoped credentials"; network secrets are
    "attached to matching requests after they leave the session"; GitHub credentials "never enter a
    session's VM" (https://code.claude.com/docs/en/claude-code-on-the-web).
  - Cloudflare Sandbox outbound workers hold secrets "the sandbox never sees"
    (https://blog.cloudflare.com/sandbox-auth/).
  - iron-proxy: sandbox holds "only opaque proxy tokens" swapped for real credentials at the proxy
    (https://hermes-agent.nousresearch.com/docs/user-guide/egress/iron-proxy).
  - Sidecar proxy with hostname egress policy and secret injection
    (https://github.com/mattolson/agent-sandbox/); survey of sandboxes doing the same
    (https://github.com/restyler/awesome-sandbox, https://github.com/bureado/awesome-agent-runtime-security).
- How each CLI fits:
  - Claude Code: `ANTHROPIC_BASE_URL` to the proxy plus a dummy `ANTHROPIC_AUTH_TOKEN`; the proxy
    swaps in the real key (API-key billing). With subscription OAuth the token must be in the
    container (the CLI does the OAuth itself), so a proxy can only hide it if it rewrites the
    `Authorization` header — technically possible but this is exactly "intermediating" session
    tokens for a hosted service (§2.1). Remote MCP `url`/`headers` deliberately read
    `ANTHROPIC_API_KEY`/`ANTHROPIC_AUTH_TOKEN` as empty (https://code.claude.com/docs/en/mcp).
  - Codex: custom `model_providers` base URL + `env_key` placeholder; ChatGPT login must live in the
    container.
  - OpenCode / Kilo: `baseURL` per provider in config, `{env:...}` placeholders.
  - Corporate proxies: `HTTPS_PROXY`/`NO_PROXY` honoured by Claude Code
    (https://code.claude.com/docs/en/self-hosted-environments); Codex `CODEX_CA_CERTIFICATE` for TLS
    interception (https://learn.chatgpt.com/docs/auth).

### 3.3 Git credentials
- GitHub App installation tokens: "The installation access token will expire after 1 hour", can be
  narrowed with `repositories`/`repository_ids` and `permissions`
  (https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app).
  Best fit for a hosted LADO: a LADO GitHub App; mint per-session, per-repo tokens; serve them via a
  git credential helper that calls the control plane (so the agent never holds a long-lived token),
  or push via a git proxy as Anthropic does.
- Deploy keys (per repo, ssh, read-only or write) for single-repo self-hosted setups.
- Forwarded ssh-agent socket (what LADO's Docker image does) — keeps the private key off the
  container but any agent can use it while mounted.
- Fine-grained PATs / `GH_TOKEN` (today's LADO default): simple, long-lived, broad; OK for (a).

### 3.4 Egress control
- Default-deny NetworkPolicy plus an allowlisting proxy (model API, git host, package registries,
  MCP hosts). Anthropic's hosted sessions use "Trusted" network access with default allowed domains
  and warn that even with network disabled "Claude Code can still communicate with the Anthropic API,
  which may allow data to exit the VM" (https://code.claude.com/docs/en/claude-code-on-the-web).
- Note the WIF note on `jti` single-use and the Codex refresh write-back: the egress proxy must allow
  the vendor's token endpoints.

## 4. Remote-running capabilities

### 4.1 Headless / no TTY
- Claude Code: `-p` (print) mode and Agent SDK; `--bare` skips `CLAUDE_CODE_OAUTH_TOKEN`
  (https://code.claude.com/docs/en/authentication). In LADO the agent runs in tmux, so it has a pty.
- Codex: `codex exec` non-interactive; API key "recommended default for automation"
  (https://learn.chatgpt.com/docs/auth; https://developers.openai.com/codex/noninteractive).
- Kilo: `kilo run --auto` (https://kilo.ai/docs/code-with-ai/platforms/cli).
- OpenCode: `opencode run` / server mode (LADO's provider already drives it this way per
  `src/lado/providers/opencode_family.py`).

### 4.2 Hooks in containers
- Claude Code hooks: five types `command`, `http` ("POSTs the JSON input to a URL"), `mcp_tool`,
  `prompt`, `agent`; they fire in `-p` runs; HTTP hooks are gated by `allowedHttpHookUrls` and only
  interpolate env vars listed in `allowedEnvVars` (https://code.claude.com/docs/en/hooks). The `http`
  type lets a remote container report status straight to a LADO control plane without a local
  `lado` process. Nothing in hooks depends on the host; they work in containers as long as the hook
  command/URL is reachable.
- Codex, OpenCode, Kilo: LADO already uses their hooks/plugins locally (see docs/design/agents.md);
  in a container they need the `lado` binary (or an HTTP endpoint) reachable from inside.

### 4.3 ACP (Agent Client Protocol)
- JSON-RPC over stdio, created by Zed (Aug 2025), now community-governed; registry launched
  2026-01-28 listing Claude Code, Codex CLI, Copilot CLI, OpenCode, Gemini CLI
  (https://zed.dev/blog/acp-registry, https://zed.dev/acp, https://zed.dev/docs/ai/external-agents).
- Launch commands (third-party table, verify): Claude via adapter `@agentclientprotocol/claude-agent-acp`
  (built on the Agent SDK), Codex via `@zed-industries/codex-acp`, `gemini --acp` (native),
  `copilot --acp --stdio` (native), `opencode acp` (native) (https://docs.rs/crate/acp-cli/0.3.1).
  Kilo: `kilo acp` (https://kilo.ai/docs/code-with-ai/platforms/cli).
- ACP is stdio-only, so remote use means LADO's in-container shim speaks ACP locally and relays over
  its own channel. Caution: the Claude ACP adapter uses the Agent SDK; Anthropic's page names the
  Agent SDK among products for which developers "should use API key authentication" — subscription
  login through an ACP adapter in a hosted product is a further legal grey zone.

### 4.4 Remote MCP (agent reaches an MCP server on another host)
- Claude Code: `--transport http` (streamable HTTP, recommended), SSE deprecated, `ws` via JSON;
  static `headers`, `${VAR}` expansion, `headersHelper` (re-run after 401/403), OAuth 2.0 via `/mcp`.
  "A `claude -p` or Agent SDK run has no `/mcp` panel, so Claude Code can't run the OAuth flow
  there" — pre-authorise interactively or use bearer headers (https://code.claude.com/docs/en/mcp).
- Codex: `[mcp_servers.x] url = ...`, `bearer_token_env_var`, `http_headers`, OAuth via
  `codex mcp login <name>` (secondary: https://www.tembo.io/blog/codex-cli-mcp,
  https://codex.danielvaughan.com/2026/05/19/codex-cli-mcp-server-management-cli-commands-oauth-streamable-http-production-patterns/).
- OpenCode: `"type": "remote"`, `url`, `headers`, automatic OAuth with Dynamic Client Registration,
  `opencode mcp auth <name>`, tokens in `~/.local/share/opencode/mcp-auth.json`
  (https://opencode.ai/docs/mcp-servers/).
- Kilo: `mcp` key in `kilo.jsonc` (OpenCode fork; same model); remote MCP OAuth noted in the runtime
  architecture doc (https://kilo.ai/docs/contributing/architecture/cli-runtime#remote-mcp-oauth).
- Implication: LADO's MCP server (`lado mcp`, today stdio per agent) can be exposed as a streamable
  HTTP endpoint with a per-agent bearer token; all four CLIs can reach it. Use bearer headers, not
  OAuth, because headless OAuth is awkward in Claude Code.

## 5. Blockers and risks for a paid hosted LADO

1. **Claude Code + operator-paid inference = prohibited** without a separate Anthropic agreement.
2. **Claude subscription in a hosted service**: allowed only as "end user signs in to the unmodified
   binary"; LADO must not collect/store/intermediate the token (no paste-your-setup-token field, no
   key-swapping proxy for OAuth tokens); operator must accept Commercial Terms. Ambiguous where the
   credential file sits on operator storage. Enforcement "without prior notice", account bans
   reported.
3. **ChatGPT subscription in a hosted service**: needs OpenAI approval (SIWC interest form for paid
   or remotely hosted apps); copying `auth.json` is unsanctioned and technically fragile.
4. **Gemini subscription**: banned; Copilot: per-seat, not shareable.
5. **OpenCode Zen/Go**: "own internal use" only; cannot be the operator's model supply.
6. **Safe model for a paid service**: BYO API keys / BYO cloud (Bedrock, Vertex, Foundry, Azure)
   per user, billed to the user; or operator API keys only for non-Claude-Code agents (Codex via
   OpenAI API, OpenCode/Kilo via provider APIs or Kilo Gateway) after confirming the provider's
   reseller terms. Self-hosted cloud mode (scenario a) is low risk for all CLIs.
7. **Technical**: refreshing logins (Codex `auth.json`, Claude `/login`) must be one per container;
   static setup-token is per-user and model-only; headless MCP OAuth is limited in Claude Code.
