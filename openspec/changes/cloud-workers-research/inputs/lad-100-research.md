# LAD-100. Облачные воркеры: исследование и план

Дата: 2026-10-18. Статус: черновик для обсуждения. Кода не меняли, трекер не трогали.

Исследование шло по пяти направлениям. Подробные отчёты (на английском, с источниками и ссылками на код) приложены отдельными артефактами:

| Артефакт | О чём |
|---|---|
| `r1-lado-coupling` | что в LADO привязано к одной машине: 16 мест с указанием `файл:строка`, «швы» для удалённого запуска |
| `r2-prior-art` | как это делают другие: около 50 продуктов и проектов, около 385 источников |
| `r3-cloud-survey` | обзор облаков, Kubernetes, песочниц, изоляции и слоёв переносимости |
| `r4-credentials` | логины агентских CLI в облаке, условия использования, секреты |

## 1. Главное в пяти пунктах

1. **Индустрия пришла к одной схеме.** «Плоскость управления» (UI, очередь задач, журнал событий, учётные записи) отделена от «песочницы», где работает агент. Песочница — это контейнер или микро-VM, одна на сессию. Код попадает туда через `git clone`, результат уходит веткой или PR. В режиме self-hosted «исполнитель» сам подключается к плоскости управления исходящим соединением, поэтому NAT не мешает. Так устроены Claude Code (self-hosted runners), Cursor, Devin, Warp и Factory.
2. **У LADO нет центрального процесса-владельца.** Все процессы работают с одним SQLite, одним tmux и одной файловой системой: CLI, UI-сервер, цикл сессии, `lado mcp` каждого агента, каждый хук. Поэтому **перенести в облако сессию целиком легко**: почти всё уже есть. А **вынести в облако отдельного воркера дорого**: нужны сетевые хуки и MCP, синхронизация git и ретрансляция терминала.
3. **Переносимость между облаками дают три стандарта: OCI-образ, Docker API (в том числе по SSH) и Kubernetes API.** Их хватает, чтобы покрыть любой VPS (Hetzner, DO, Selectel, Yandex), любой Kubernetes (k3s у себя, управляемые кластеры, российские облака) и песочницы. Песочницы при этом подключаются адаптерами, а не кодом ядра. Привязываться к проприетарным API песочниц (E2B, Modal, Daytona) не нужно. Daytona в 2026 году к тому же закрыла исходники.
4. **Требование «любой провайдер» сохраняется, если оставить CLI неизменными внутри tmux, как сейчас.** Свой агент или чтение экрана проиграли: AgentAPI от Coder, который читал экран, заархивирован. Наш принцип «события, а не экраны» подтверждается опытом рынка.
5. **Главное ограничение платного варианта юридическое, а не техническое.**
   - **Anthropic** прямо запрещает платформе платить за Claude-инференс пользователей или перепродавать его. Хранить их токены claude.ai тоже нельзя. Разрешено одно: пользователь сам входит своей подпиской в неизменённый `claude` на хостинговой платформе.
   - **OpenAI**: вход «Sign in with ChatGPT» для платного хостинга требует заявки и одобрения.
   - **Gemini CLI**: OAuth из сторонних программ запрещён.
   - Безопасная модель для платного сервиса — **BYOK**: пользователь приносит свой ключ API или облачный аккаунт (Bedrock, Vertex, Azure), и платит за модели сам.

## 2. Какие решения бывают

### 2.1 Где запускать

| Вариант | Привязка | Можно у себя | Под долгую интерактивную сессию | Вывод |
|---|---|---|---|---|
| **Docker-хост по SSH** (любой VPS или домашний сервер; Podman так же) | нет | да | отлично | **первый бэкенд** |
| **Kubernetes** (k3s, EKS/GKE/AKS, DO/Scaleway/OVH, Yandex/Selectel/VK Cloud/Cloud.ru) | нет | да | хорошо: StatefulSet из одного пода плюс PVC | **второй бэкенд** |
| `kubernetes-sigs/agent-sandbox` (CRD Sandbox, пулы тёплых подов, pause/resume, gVisor/Kata) | нет | да | создан ровно под эту задачу | режим k8s-бэкенда, позже; OpenHands уже на нём |
| VM через API облака | слабая (свой SDK у каждого) | — | хорошо | «Docker-хост плюс создание машины»: помощник, а не отдельный бэкенд |
| Fly Machines и Sprites (Firecracker, suspend/resume) | средняя | нет | хорошо, дёшево в простое | позже, как вариант «ноль администрирования» |
| Песочницы SaaS: E2B, Modal, Runloop, Morph, Northflank, Daytona | высокая | частично | у части лимит 24 часа | только адаптером, по запросу |
| Serverless: Cloud Run, Fargate, ACI | средняя | нет | плохо: WebSocket обрывается через час, нет suspend | не подходит |
| Nomad | — | да | — | не нужен: лицензия BSL, мало пользователей |

### 2.2 Слои переносимости

- **OCI-образ.** У нас он уже есть (Docker-эпик LAD-52): один образ с четырьмя CLI, amd64 и arm64. Это общая единица для всех вариантов.
- **devcontainer.json.** Даёт «бесплатный» запуск LADO в DevPod, Coder и Codespaces со всеми их провайдерами без кода интеграции. Это дёшево, и стоит сделать сразу.
- **Coder (Terraform-шаблоны)** — для организаций, где он уже есть. Хватит примера шаблона.
- **DevPod.** Лучшая модель «сменить облако одним флагом», но разработка с 2025 года почти стоит. Берём идею (маленький внешний «провайдер-CLI»), а не зависимость.
- **Pulumi Automation API и OpenTofu** нужны только для создания машин. Pulumi удобнее из Python.
- **Crossplane и libcloud** не нужны.

### 2.3 Изоляция

- Для одного пользователя на своём VPS достаточно отдельной VM и обычного контейнера.
- Для общего хоста и тем более для платного сервиса нужна изоляция уровня VM: gVisor (без KVM), Kata или Firecracker. К ней добавляются ограничение исходящего трафика по списку, пользователь без root, токены с узкими правами и остановка по простою.
- Docker-сокет хоста по умолчанию не монтировать. Если агентам нужен Docker внутри, использовать Sysbox.

## 3. Что из LADO можно запускать в облаке: четыре точки разреза

| Разрез | Что где работает | Что менять в LADO | Размер |
|---|---|---|---|
| **A. Вся сессия в удалённой «коробке»** | LADO, UI и все агенты в одном контейнере, VM или поде. Человек открывает UI в браузере | Ядро не меняется. Нужны TLS и нормальный вход в UI, репозитории из git URL вместо монтирования папки, постоянный том, рецепты запуска (compose на удалённом хосте, Helm или манифест k8s, devcontainer) | S–M |
| **B. UI удалённо, исполнение локально** (или наоборот) | только представление | TLS и вход; фактически это то же, что десктоп-приложение | S |
| **C. Все агенты одной сессии на удалённом узле**, плоскость управления отдельно | UI и БД в одном месте, tmux, worktree и CLI на узле | интерфейс «бэкенда исполнения» ниже `providers/`; хуки и MCP по сети с токеном для каждого агента; ретрансляция терминала; демон узла с исходящим соединением. Git на узле работает как сейчас (worktree рядом) | M–L |
| **D. Отдельные воркеры удалённо** (смешанная сессия), полное разделение «управление / исполнение» | супервизор локально, часть воркеров в облаке | всё из C плюс синхронизация веток (clone и push/fetch), heartbeat, реестр узлов. Ноутбук-«управление» должен быть доступен узлу | L–XL |

**Ответ на вопрос «что именно запускать в облаке»:** правильная целевая архитектура — D, плоскость управления и плоскость исполнения. При этом локальный запуск становится одним из узлов, «локальным узлом». Идти к ней стоит через A и C. Каждый шаг даёт работающий результат и не трогает локальный режим.

### Уже есть в коде, можно переиспользовать

- **Интерфейс провайдеров:** `Capabilities` и разбор событий в `providers/base.py`.
- **Идентичность агента:** идентификатор запуска `agents.instance`. Это готовая основа для токена агента.
- **Ленты событий:** `feed.Source`. В его docstring уже упомянуты события удалённых воркеров.
- **Хранилище артефактов:** протокол `artifacts.Store`, его можно вынести в сервис.
- **Авторизация:** `server/auth.py`, единое место авторизации UI. Токен и Bearer уже есть, OpenAPI тоже.
- **Секреты:** папка `LADO_ENV_DIR` ложится на секреты Kubernetes или Docker один к одному.
- **Версии:** `SchemaError` — образец проверки версии протокола между управлением и узлом.
- **ACP (этап 8 ROADMAP):** запланирован «за тем же интерфейсом». Это тот же шов, так что интерфейс бэкенда стоит проектировать сразу с прицелом на три реализации: tmux, удалённый узел и ACP.

## 4. Логины агентов и деньги

| Сценарий | Claude Code | Codex | Kilo / OpenCode | Gemini CLI |
|---|---|---|---|---|
| (a) пользователь сам запускает LADO в своём облаке со своей подпиской | можно: `claude setup-token` или `/login` в контейнере | можно, но `auth.json` — один на машину, его нельзя делить между репликами | можно | только API-ключ или Vertex |
| (b) наш хостинг, подписка пользователя | только если пользователь сам входит в неизменённый `claude`. Хранить или вставлять его токен нельзя. Нужно письменное подтверждение Anthropic | только по заявке и одобрению OpenAI | Kilo разрешает; OpenCode Zen/Go — нет | нельзя |
| (c) наш хостинг, наши ключи, мы берём деньги | **запрещено** без отдельного договора с Anthropic | похоже, разрешено по Services Agreement (уточнить) | Kilo разрешает | API-ключ — да |

Отсюда:
- **Self-hosted облако (сценарий a) юридически безопасно** для всех CLI. С него и начинаем.
- **Платный сервис** строится по модели BYOK: свой ключ или облачные учётки пользователя. Ключи держит исходящий прокси, который подставляет их в запросы (так делают Anthropic, Cloudflare и Docker Sandboxes), поэтому агент самих ключей не видит. Доступ к git — через GitHub App с токенами на один час. Подписки Claude в платном сервисе — только через собственный вход Anthropic, и только после письменного «да» от них.
- **Рынок предупреждает.** Хостинговые обёртки над чужими CLI в 2026 году в основном закрылись или сменили курс: Terragon, Bloop, Omnara, Crystal. Платный вариант — гипотеза, которую надо проверять дёшево.

Технические ограничения по логинам:
- Обновляемые логины (Codex `auth.json`, Claude `/login`) нужны в отдельной копии на каждый контейнер.
- `CLAUDE_CODE_OAUTH_TOKEN` статичен год и годится для «коробки».
- Все четыре CLI поддерживают удалённый MCP по HTTP с заголовком Bearer. Это нужно для разрезов C и D.
- У Claude Code есть хуки типа `http`.
- Всё это надо проверить руками на тех версиях CLI, с которыми тестируется LADO.

## 5. Принципы решения

Принципы проверены на ваших критериях:

1. **Облако — дополнение.** Локальный режим остаётся режимом по умолчанию и не меняется. Каждый шаг выпускается так, что существующий пользователь ничего не замечает.
2. **Без привязки к облаку.** Ядро знает только «бэкенд исполнения» с маленьким набором операций: создать, старт/стоп/пауза, статус, exec/attach, проброс порта, удалить. Каждый бэкенд громко сообщает, чего не умеет, по принципу No silent drops. Конкретные облака подключаются бэкендами (Docker по SSH, Kubernetes) или внешними адаптерами в духе провайдеров DevPod, а не кодом ядра.
3. **Любой провайдер.** В облаке те же неизменённые CLI в tmux, тот же образ со всеми CLI, те же хуки и MCP. Только MCP и хуки идут по сети.
4. **Компонентность.** UI, плоскость управления (БД, цикл, артефакты) и исполнение — отдельные компоненты. Каждый можно поставить где угодно: всё локально, всё в облаке, UI локально и агенты в облаке.
5. **Заранее готовы к платной версии**, не строя её сейчас:
   - секреты не хранятся в плоскости управления, есть только ссылки на них;
   - у каждого агента свой токен;
   - события расхода (время узла, токены) пишутся в журнал;
   - в схеме данных есть поле владельца или арендатора;
   - API UI стабилен, с OpenAPI.

## 6. План по шагам

Каждый шаг — это работающая поставка, которая не ломает локальный режим. Порядок работы как в Docker-эпике: план лежит рядом с исследованием, в трекер попадает только следующая задача, после каждого шага план пересматривается.

### Шаг 0. Проверки до проектирования (исследование руками, без кода в продукте)
- **MCP по HTTP:** работает ли он с заголовком Bearer у каждого CLI на тестируемой версии.
- **HTTP-хуки Claude Code:** их поведение.
- **Задержки:** время оборота хука по сети против лимита в 60 секунд.
- **Codex `auth.json` в контейнере:** что происходит с ним при обновлении токена.
- **Запуск образа LADO на удалённом Docker-хосте:** через `DOCKER_HOST=ssh://` и в k3s (PVC, перезапуск пода).
- **Выбор синхронизации git для разреза D:** push в origin, отдельный bare-репозиторий LADO или fetch с узла.
- **Юридические вопросы** (только если идея платного сервиса жива): письмо в Anthropic про сценарий (b), заявка в OpenAI на «Sign in with ChatGPT», консультация юриста.

### Этап A. «LADO в облаке целиком» (разрез A; ядро не меняется)
- **A1. Безопасный удалённый UI.**
  - TLS: встроенный или через обратный прокси, с документированным рецептом.
  - Вход в UI вместо одного токена в URL.
  - Ограничение терминального WebSocket: он даёт браузеру права оболочки.
  - Сначала эту часть надо закрыть, потом звать в облако.
- **A2. Репозитории из git URL как основной путь в облаке** (клонирование уже есть). Постоянный том `/home/lado` для состояния, логинов и mise.
- **A3. Рецепты запуска.**
  - compose для удалённого Docker-хоста (VPS);
  - Helm-чарт или манифест для Kubernetes (StatefulSet из одного пода плюс PVC);
  - `devcontainer.json` для DevPod, Coder и Codespaces;
  - документация «LADO на VPS» и «LADO в Kubernetes».
- **A4. Логины в «коробке».** Ввести `CLAUDE_CODE_OAUTH_TOKEN` или API-ключи через `LADO_ENV_DIR` или секреты k8s; Codex — T15 Docker-эпика.

**Итог этапа A:** пользователь за 10–15 минут поднимает LADO на любом VPS или в любом Kubernetes со всеми CLI и работает из браузера. Локальная установка не меняется. Этап продолжает Docker-эпик LAD-52.

### Этап B. Внутренние швы (рефакторинг без изменения поведения)
- **B1. Интерфейс «бэкенда исполнения» ниже `providers/`.**
  - Операции: запустить, ввести текст, подключить терминал, жив ли, остановить.
  - tmux становится первой реализацией; поведение не меняется.
  - Интерфейс проектируется вместе с будущим ACP-рантаймом.
- **B2. Токен для каждого агента** на основе `agents.instance`. MCP-сервер LADO доступен и по HTTP; локально по-прежнему stdio.
- **B3. Хуки:** доставка событий через API LADO как вариант к прямой записи в SQLite. Единственный писатель в БД — плоскость управления, для удалённых агентов.
- **B4. «Пакет запуска»:** провайдер собирает конфиги, промпт и навыки в переносимый пакет, а не пишет пути в `LADO_HOME`.

**Итог этапа B:** локально всё как раньше, но удалённый узел стало возможно подключить. Каждый пункт — отдельная задача с полным набором тестов.

### Этап C. Удалённый узел для сессии (разрез C)
- **C1. `lado node`:** демон на узле. Он держит tmux, worktree и CLI и подключается к плоскости управления **исходящим** соединением, поэтому NAT и поды не мешают. Проверка версии протокола.
- **C2. Бэкенд «Docker по SSH»:** любой VPS, есть опция gVisor или Sysbox.
- **C3. Бэкенд Kubernetes:** под плюс PVC, затем режим agent-sandbox (пауза, тёплые пулы).
- **C4. Терминал агента в UI через узел.** Остановка, возобновление и обновление узлов.
- **C5. Выбор места при старте сессии:** `lado start --on <бэкенд>` и такой же выбор в UI. Конфиг бэкендов в `~/.lado`; секреты хранятся ссылками.

**Итог этапа C:** UI и данные у пользователя, тяжёлая работа агентов в облаке; облако меняется одной настройкой.

### Этап D. Смешанные сессии (разрез D; только если понадобится)
Отдельные воркеры размещаются удалённо (`spawn_worker(..., placement=...)`), ветки синхронизируются через git, есть heartbeat и реестр узлов. Это самый дорогой этап. Решение принимать по итогам C.

### Этап E. Платный сервис (только идея; решение после A–C и ответа юристов)
- Мультиарендность: по сессии или «коробке» на пользователя, изоляция уровня VM.
- Исходящий прокси с ключами BYOK и GitHub App.
- Учёт и биллинг на основе журнала событий расхода.
- Регистрация и вход.
- Сначала стоит проверить на рынке дешёвый вариант: «управляемая коробка» (этап A, развёрнутая нами для пользователя). Отдельную облачную платформу строить потом.

## 7. Риски

- **SQLite с многими писателями** не переносится между хостами. Лечится единственным писателем (B3), а не удалённой БД.
- **Git** — самая большая дыра для разреза D. До этапа D её не открываем.
- **Безопасность UI в сети.** Сейчас это HTTP с токеном, а терминал фактически даёт оболочку. A1 обязателен до любых облачных рекомендаций.
- **Подписки.** Лимиты Pro/Max рассчитаны на «обычное индивидуальное использование». Много параллельных агентов в облаке на одной подписке могут упереться в лимиты или вызвать санкции.
- **Нестабильность рынка песочниц.** Daytona закрыла код, DevPod стоит, OpenAI покупает Ona. Поэтому опора — на стандарты (OCI, Docker API, k8s API), а не на вендоров.
- **Сеть из России:** Cloudflare Tunnel и Tailscale могут быть недоступны. Нужен базовый путь без них: SSH-туннель или Headscale.
