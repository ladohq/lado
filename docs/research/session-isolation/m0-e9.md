# M0, E9: the runc step, a container per session without gVisor

Date: 2026-11-27. Brief: [E9](m0-experiments-brief.md#e9-the-runc-step); threshold:
[the plan, section 5](../session-isolation-plan.md#5-the-m0-experiments). Machines:
GitHub's hosted runners `ubuntu-24.04`, a private repository `kao73/gvisor-spike`, branch
`m0-e9` (E14's scripts reworked for runc). Runs:
- `45989621271`: all phases;
- `45992887853`: simple settings for the open rows, nested runc with `SYS_PTRACE`;
- `45995957706`: nested runc with `SYS_PTRACE` and `SYS_CHROOT`.

Translated from the Russian report; all tables and numbers are kept. The report refers to
the raw logs in `runs/<id>/e9-X64/` (the `logs/` files below) and to the scripts in
`repo/m0/e9/`; **they are not committed to this repository**.

## 1. Summary

- **On the host (the own-server design: scheme B with the hardening, `--runtime=runc`) more
  is open than under runsc:**
  - Docker's DNS answers for external names: a leak channel;
  - root has raw and packet sockets (`NET_RAW` is among Docker's default capabilities);
  - the machine's DMI identifier, the host's `boot_id` and the paths
    `/var/lib/docker/overlay2/…` in mountinfo are visible.

  Processes, files, the other session, the host's services, metadata, IPv6, the internet
  directly and writing to `/proc/sys` are closed the same as under runsc.
- **A simple setting closes three of the five open rows:**
  - `--dns 192.0.2.1` (DNS);
  - `--cap-drop NET_RAW` (raw sockets);
  - `--tmpfs /sys/devices/virtual/dmi:ro` (DMI).

  A session works with them: 25 of 29 checks, and all 4 failures are user namespaces.
  **Two information leaks remain without a simple setting:** the host's `boot_id` (runc
  does not allow mounting anything over `/proc/sys`) and the host's paths in mountinfo.
  They give no access, they only identify the host.
- **Compatibility is worse than under runsc:** `codex sandbox`, bwrap and `unshare -U` do
  not work under runc. User namespaces are refused by Docker's seccomp; without seccomp,
  AppArmor or the kernel stops it further on. Codex in such a session would have to run
  without its own sandbox.
- **The nested form (Docker Desktop) was not checked: runc in the R+net runner does not
  start.** Three variants were tried, each reached a new error:
  1. six capabilities: `open /proc/<pid>/ns/mnt: permission denied`;
  2. `+SYS_PTRACE`: `setns: operation not permitted`;
  3. `+SYS_PTRACE +SYS_CHROOT`: `unable to join session keyring` (the runner's seccomp
     refuses `keyctl`).

  So runc inside the runner needs a wider runner than runsc does.
- **Decision by the threshold: the strict threshold is not passed** (5 rows open on the
  host, the nested form does not start). **By the softened threshold ("closed by a simple
  setting") the host still has two information leaks without access: `boot_id` and the
  paths in mountinfo.** This is for the human to decide. A nested runc step on Docker
  Desktop does not work in its present form.

Azure VM (`Standard_D2ds_v6` / `D2ads_v6`; in run 1 Intel Xeon Platinum 8573C), 2 vCPU

## 3. What was done

### 3.1 The form on the host: scheme B (`host.sh`, `logs/e9-21-host.md`, run 2)

The design and the targets are as in [E14](m0-e14.md). S1 and S2 in their own bridge
networks, the proxy in `e9-egress`, `DOCKER-USER` rules over the pool. The protection
variants:
- "no hardening": scheme B only;
- "hardening": plus `INPUT`/`ip6tables` REJECT from the session bridges;
- "dns": plus `--dns 192.0.2.1`;
- "simple": plus `--dns 192.0.2.1 --cap-drop NET_RAW --tmpfs /sys/devices/virtual/dmi:ro`.

Users: uid 1000 and root with Docker's default capabilities (`a80425fb`, which includes
`NET_RAW`). The runsc baseline was taken in the same run.

How to read the kernel rows:
- "closed" for runc means Docker's seccomp/AppArmor do not let the call into **the host's
  real kernel**;
- "works" for runsc means the sentry handled the call; the host's kernel does not see it;
- attacks on the kernel are outside E9's scope (T5).

What is applied to a runc session (`/proc/self/status` and from outside): `Seccomp: 2`, one
filter, AppArmor `docker-default (enforce)`, `NoNewPrivs: 0`. Under runsc on the host the
processes' AppArmor is `unconfined`, as in E14.

**What refuses user namespaces under runc** (uid 1000, `unshare -U -r` and bwrap):

| setting | `unshare -U -r` | bwrap |
|---|---|---|
| default | `Operation not permitted` | No permissions to create new namespace |
| `apparmor=unconfined` | the same | the same |
| `seccomp=unconfined` | **works** (uid 0 in the userns) | `Failed to make / slave: Permission denied` |
| both `unconfined` | `write /proc/self/uid_map: Operation not permitted` | `loopback: Failed RTM_NEWADDR` |

The first barrier is Docker's seccomp. Removing it for the agent's sandbox means opening the
kernel. There is no simple setting.

**Compatibility with `--dns 192.0.2.1`** (`logs/e9-30-compat.txt`, through the proxy): 25
of 29 OK:
- working: git clone/status/worktree, tmux and `-L lado`, `uv sync` + `lado --version`
  (0.49.0), `npm ci`, gcc, `--version` and the screens of the four CLIs, inotify;
- **not working:** `codex sandbox -- true`, `codex sandbox` with `touch /etc/x`, bwrap and
  `unshare` (see above).

The session's closed DNS does not get in the way: everything goes through the proxy.

**cgroup limits** (a side note): `--memory 256m` and 600 MB give `rc=137`; `--cpus 0.5`
gives 1.0 s against 0.57 s. They work.

### 3.2 The nested form: R+net, the sandbox through runc (`nested.sh`, `nested-in.sh`)

Round 2's runner (`runner.json`, six capabilities, `no-new-privileges`,
`apparmor=unconfined`), a netns per sandbox and round 2's "proxy only" rules. The proxy is
outside, in `e9-egress`. The runc sandbox's spec repeats a Docker session:
- Docker's default seccomp profile, converted to OCI the way dockerd does it
  (`nested_spec.py`);
- Docker's default capabilities intersected with the runner's bounding set: `NET_RAW,
  SETGID, SETUID, SETFCAP`;
- Docker's masked and read-only paths;
- `noNewPrivileges`.

The runner's cgroup2 is mounted ro; `mount -o remount,rw /sys/fs/cgroup` succeeds.

| attempt | runner | runc 1.5.3's error |
|---|---|---|
| 1 | R+net (6 capabilities) | `error spawning mount remapping thread: mount source thread: open container mntns: open /proc/<pid>/ns/mnt: permission denied` |
| 2 | + `SYS_PTRACE` | `… join container mntns: setns: operation not permitted` |
| 3 | + `SYS_PTRACE` + `SYS_CHROOT` | `error during container init: unable to join session keyring: unable to create session key: operation not permitted` (the runner's seccomp refuses `keyctl`) |

As the brief requires, I stopped after three variants. The next step would have been `runc
run --no-new-keyring`; after that the runner's seccomp would probably need changes. Either
way, a runner for runc is wider than R+net by at least `SYS_PTRACE` and `SYS_CHROOT`.

The limits inside the runner could not be set up: moving the runner's processes into a leaf
cgroup failed (`echo pid > init/cgroup.procs`: `Operation not supported`). Without that the
controllers cannot be enabled for the children, and runc with `memory.limit` fails:
"cannot enter cgroupv2 … with domain controllers". That is E8's subject.

**The runsc baseline in the same runner** (runs 2 and 3, `logs/e9-31-nested.md`):
- smoke 5 of 5;
- everything closed except two rows that are open without the hardening (round 2's rules):
  - **the runner's services over IPv4**: round 2's rules refuse `INPUT -i veth+`; the "no
    hardening" stage does not have that rule;
  - **over IPv6 link-local**: from the sandbox the runner's `[fe80::…%eth0]:9997` answers
    200. Round 2's rules have no `ip6tables`.
- With the hardening (`INPUT` REJECT, `ip6tables` INPUT/FORWARD REJECT from `veth+`) both
  rows are closed.

## 4. What it means for the plan

A proposal for the supervisor:
- **The runc step of the ladder Q2 is not accepted by the strict threshold.** If the human
  softens the threshold to "closed by a simple setting", the step is possible on an own
  server. A runc session then gets:
  - `--dns 192.0.2.1`;
  - `--cap-drop NET_RAW`;
  - `--tmpfs /sys/devices/virtual/dmi:ro`;
  - scheme B with `INPUT`/`ip6tables` REJECT.

  The `boot_id` and overlay2 path leaks remain. They only identify the host; there is no
  access to its data. Whether that is acceptable is for the human to decide.
- **The cost of the runc step for the agents:** `codex sandbox` and bwrap do not work. Codex
  in such a session runs without its own sandbox: the container is the sandbox. In M4 the UI
  and `lado doctor` must say so.
- **On Docker Desktop (the nested form) there is no runc step in its present form:** runc
  does not start in R+net, and widening the runner (`SYS_PTRACE`, `SYS_CHROOT`, `keyctl`)
  for a step weaker than runsc is a bad deal. On Docker Desktop the ladder goes straight to
  runsc. An alternative for M4 is a Docker container per session through the socket; that
  is E14's variant with runc, but on Docker Desktop the socket equals access to its VM.
- **R+net (and E3) needs `ip6tables` rules:** without them the sandbox reaches the runner's
  services over IPv6 link-local even under runsc. Round 2's line "the rules hold against
  root" is true only for IPv4; the plan already notes this.
- **A correction to E14's report:** it says that Docker 28.0.4 has no `NET_RAW` by default.
  That is wrong. A runc container has `NET_RAW` (`CapEff a80425fb`). Under runsc it is
  absent because runsc without `--net-raw` drops it itself. E14's conclusion does not
  change.

## 5. Problems and surprises; what was not done

- The nested form was not finished (section 3.2); three variants, then a stop.
- The cgroup limits in the nested runner could not be set up (that is E8).
- In run 1 the nested sandbox's spec did not include `NET_RAW` in Docker's capabilities.
  Fixed in run 2, but the nested runc never got as far as the probes.
- The compatibility repeat "on an unrestricted network" also ran with `--dns 192.0.2.1`, so
  without the proxy even git clone failed. One more confirmation that DNS is closed. The
  bwrap/unshare failures in it are the same.
- The `boot_id` row of the table is marked "leak" in every column. Under runsc each sandbox
  gets its own random `boot_id`, different from the host's: that is not a leak.
- x86_64 and Azure only. arm64 was not done: the rows depend on Docker and the kernel, not
  on the architecture.

## 6. Cleanup

Each run ends with an `undo` phase:
- removed: the containers, networks, volumes and images labelled `lado.m0=e9`, the pulled
  images and the buildx builder;
- removed: the rules `E9-SESS`, `DOCKER-USER`, `INPUT` and `ip6tables`;
- runsc removed, the absence of `daemon.json` restored, dockerd restarted;
- the host's markers and services removed.

The snapshots before and after matched in all three runs (`snapshots match`). The host is a
single-use GitHub VM. Nothing was sent to `ladohq/lado`. Commits only to
`kao73/gvisor-spike`, branch `m0-e9`. On this branch the `spike-runner` image got runc 1.5.3
(the release's sha256 checked).
